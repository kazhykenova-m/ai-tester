# AI Tester — Telegram-бот для команды

Менеджер присылает URL, выбирает сценарий и устройство. Бот проходит путь
пользователя в Chromium, а Gemini принимает решения и рассматривает скриншоты.
Разработчик получает короткий итог в Telegram и ZIP: report.html, report.md,
report.json и скриншоты дефектов. Успешные клики не попадают в отчёт.

## Что реализовано

- Магазин: каталог → поиск/фильтры → товар → вариант → корзина → количество → удаление.
- Формы и модалки: видимость, открытие/закрытие, обязательность и доступная валидация.
- Свой сценарий обычным текстом.
- Компьютер 1366×850, телефон 390×844 или оба, отдельные отчёты.
- Ошибки JS, console.error, HTTP и запросов; визуальные дефекты по скриншотам.
- Правка: категория, приоритет, фактическое и ожидаемое поведение,
  страница, доказательство, шаги воспроизведения, скриншот для визуальных дефектов.
- Очередь SQLite, один браузерный процесс за раз, /status, /cancel,
  лимит 30 минут, восстановление статусов после перезапуска.
- Только личные чаты и сотрудники из TELEGRAM_ALLOWED_USERS.
- /code: ZIP с исходниками до 10 МБ. Синтаксис Python, JS, PHP, JSON.
  Код не исполняется. TS/JSX/CSS требуют инструментов самого проекта.
- Автоудаление завершённых отчётов через 7 дней (настраивается).

## Запуск на сервере (Docker Compose)

1. Создай Telegram-бота в @BotFather командой /newbot. Сохрани выданный токен.
2. Узнай числовые Telegram ID сотрудников. Нужен ID пользователя, не ID бота.
3. В каталоге проекта скопируй .env.example в .env.
4. Заполни TELEGRAM_BOT_TOKEN, GEMINI_API_KEY и TELEGRAM_ALLOWED_USERS.
   Ключи вводи в .env на сервере, не отправляй в чат и не коммить.
5. Если проверяешь staging, перечисли его точные хосты в TEST_WRITE_HOSTS,
   например TEST_WRITE_HOSTS=shop.test.example.com. Никаких wildcard. Если staging использует отдельный тестовый API-хост,
   его также нужно добавить. Запросы изменения данных на прочие хосты блокируются.
6. Запусти:

```bash
docker compose up -d --build
docker compose logs -f
```

Нужен Linux-сервер с Docker, доступом к Telegram, Gemini и проверяемым сайтам.
Входящий публичный порт, HTTPS-домен и webhook не нужны: используется long polling.
Запускай только один экземпляр бота на один токен. Если у бота уже был webhook,
его нужно отключить перед long polling.

В Telegram: /start → /test → ссылка → сценарий → устройство → запуск.
Для проверки кода: /code → ZIP. /cancel отменяет текущие и ожидающие задачи сотрудника.

REPORT_RETENTION_DAYS=7 меняет срок хранения. Отчёты после отправки в Telegram
остаются в переписке; срок хранения сервера на них не влияет.
Переходы и скриншоты могут содержать данные сайта: используй тестовые аккаунты
и тестовые данные. Текст и скриншоты отправляются в Gemini для анализа.

## Режим доступа к сайту

По умолчанию разрешены GET/HEAD/OPTIONS, а POST/PUT/PATCH/DELETE блокируются.
Это ограничивает проверку корзины, отправки форм, авторизации и некоторые API
каталога. Такие блокировки отмечаются как ограничения проверки, а не ошибки сайта.
Для полноценного пути используй staging и TEST_WRITE_HOSTS. Заказы, платежи
и заполненные заявки исключены из сценариев, даже на тестовом домене.

WebSocket и service workers отключены: realtime-состояния не проверяются.
Внутренние адреса и служебные IP отсекаются до запросов, но эта проверка DNS
не заменяет сетевую изоляцию от DNS rebinding. Размещай worker на отдельном
сервере без доступа к внутренней инфраструктуре и без облачных credentials.
Read-only относится к HTTP-методам: сайт с изменением данных через GET может
иметь побочные эффекты. Для неизвестных сайтов безопаснее отдельная тестовая копия.

## Что считать результатом

Это помощник QA, а не гарантия полного покрытия. Проверяются только реально
посещённые экраны и состояния. Пустой список дефектов при незавершённом сценарии
не означает исправность сайта. Приоритеты визуальных дефектов предлагает ИИ,
их нужно подтвердить. Ошибки сторонних ресурсов могут не влиять на основной путь.

Нет автоматической сверки с макетом Figma, полноценной проверки качества/безопасности
исходников, реального iOS Safari, авторизации через сохранённые аккаунты,
CAPTCHA и автоматического создания тикетов в трекере. Наличие этих проверок
не утверждается в отчёте.

## Разработка и локальный запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
playwright install --with-deps chromium
PYTHONPATH=src python -m ai_tester.bot
python -m pytest -q
python -m ruff check .
```

При запуске без Docker оставь BOT_DATA_DIR=bot-data (относительный каталог).
Для /code установи Node и PHP CLI. Docker устанавливает их сам.
Артефакты задач хранятся в bot-data/<номер-задачи>. worker.log содержит
техническую причину сбоя и не отправляется менеджеру.

Старый CLI и GitHub Actions сохранены для разработчика. CLI запускается
напрямую и не применяет read-only guard Telegram-worker; используй только staging:

```bash
PYTHONPATH=src python scripts/run_agent.py scenarios/site_audit.md --url https://example.com --vision --mobile --headless
```

## Проверено при сборке

25 автоматических тестов: фильтрация отчётов, экранирование HTML, доступ
к боту, очередь и отмена, запрет внутренних адресов, синтаксический анализ
без исполнения исходников, цикл сценария и сохранение только дефектных скриншотов.
Ruff прошёл. Тесты цикла браузера используют подставные объекты Playwright.
Полный live-запуск Telegram/Gemini и Docker-build ещё не выполнялись:
нет токенов; загрузка Chromium в среде сборки завершилась ошибкой.
Перед командным использованием нужен один smoke-тест на staging.
